# 安全检测报告填写规范

报告定位：让管理层看懂风险等级、让开发人员能复现并修复、让测试/甲方明确覆盖范围与结论。报告不是漏洞罗列。

## 正式报告结构（公司统一模板）

正式结论报告固定使用《系统上线安全检测和安全措施有效性验证报告》结构（模板：assets/templates/结论报告.md，转换后自动带封面、声明、目录）：

| 章节 | 内容要求 |
|---|---|
| 基本信息表 | 报告编号、密级、系统/单位信息、等保定级、被测地址、评估起止日期、本次上线范围 |
| 报告概述 | 评估目的、依据标准、评估范围（**未覆盖部分如实声明**，免责） |
| 评估概述 | 系统概况、评估环境与场所、评估过程时间线 |
| 评估方法 | 四类方法（访谈/文档查验/配置核查/工具测试）+ 结论判定口径（符合/部分符合/不符合/不适用） |
| 控制项结果记录 | 每个控制域一张表：序号/控制项/检测要点/验证方法/结果记录/结论，共 12 个控制域 |
| 风险识别与整改建议 | 对部分符合/不符合项逐条登记：风险编号（R-XXX）、关联控制项、描述、等级、整改建议与时限 |
| 评估结论 | 总体结论（具备/整改后具备/不具备上线条件）+ 签署表 |
| 附录 A 证据清单 | 证据编号（E-XXX）、名称、格式、关联控制项 |
| 附录 B 检测工具与版本 | 工具名称、版本、用途阶段（T-XXX），供复测与审计比对 |
| 附录 C 漏洞明细 | 每条漏洞按八要素完整撰写 |
| 附录 D 使用说明 | 定稿前删除 |

控制域不适用时的口径：平台托管项目的中间件安全、小程序的 IPv6 支持度、纯展示站的个人信息保护，结论填「不适用」并在结果记录列写明理由（责任边界/范围不涉及），不得留空。机房及物理环境由云服务商或本地机房责任方承担时同样判「不适用」并写明责任边界。整体结论需对齐等保口径时按「符合/基本符合/不符合」三档映射并单独列示重大风险隐患（GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》，现行，全文见全国标准信息公共服务平台 openstd.samr.gov.cn）；等保测评报告由测评机构另行出具。

## 漏洞八要素（附录 C 每条必备，缺一不可）

1. **漏洞名称与编号**：简明，如「用户身份令牌硬编码导致任意用户登录」，编号 SEC-001。
2. **风险等级**：严重/高/中/低（附 CVSS 3.1 评分与向量串）。
3. **涉及位置**：具体页面、接口 URL、代码文件路径与函数名/近似行号。
4. **漏洞描述与原理**：说明代码/配置如何实现、为何构成漏洞，可附关键代码片段。
5. **复现步骤**：逐步描述，精确到请求参数、操作路径、预期与实际响应，开发照做即可复现。
6. **请求/响应证据**：抓包报文关键片段或截图（报告放编号，附录 A 登记，证据文件按编号归档在项目 02_检测过程 目录）。
7. **影响范围**：直接后果（数据泄露/资金损失/权限失控）与业务影响；可写攻击链组合效果。
8. **修复建议**：具体可落地。反例「不要硬编码」；正例「密钥仅存服务端环境变量，通过带鉴权的接口动态下发；使用 code2session 管理会话」。

## 风险等级准则（四级，须写明定义，不凭主观打分）

| 等级 | CVSS | 判定标准 | 修复时限建议 |
|---|---|---|---|
| 严重 | 9.0–10.0 | 可被外部直接利用，导致数据泄露/系统失陷/资金损失，如 SQL 注入、任意文件上传、越权、支付篡改 | 上线前必须修复 |
| 高 | 7.0–8.9 | 可造成较大影响但需一定条件，如存储型 XSS、弱口令、敏感信息明文传输 | 上线前修复或接受风险并由管理层签字 |
| 中 | 4.0–6.9 | 影响有限或利用难度高，如 CSRF、部分信息泄露、缺少速率限制 | 制定计划限期修复 |
| 低 | 0.1–3.9 | 轻微风险/最佳实践缺失，如错误堆栈泄露、缺少安全响应头 | 择机优化 |

修复优先级原则：能被外部直接利用且导致数据泄露/系统沦陷的漏洞，无论数量一律排最前。

复测判定口径：已修复 / 修复不完整 / 未修复，逐条对应原报告风险编号，证据独立编号（E-R-XXX）。

## 撰写质量检查清单

- [ ] 版本号明确（修复后靠版本对应关系做回归验证，缺版本号报告失效）。
- [ ] 测试范围为「覆盖 + 未覆盖」双向声明，避免后续扯皮。
- [ ] 每条漏洞八要素齐全，复现步骤可操作。
- [ ] 风险等级有定义依据，不用主观感受打分。
- [ ] 修复建议具体到代码/配置层面，附参考实现。
- [ ] 控制域结论无空白：符合/部分符合/不符合/不适用四选一。
- [ ] 有整体评估与明确上线结论，不停留在「发现了什么」。
- [ ] 公司抬头、报告编号、出具日期、密级填写完整。
- [ ] 证据编号 E-XXX 与风险编号 R-XXX 交叉引用一致，证据文件已归档。
- [ ] 报告引用了权威标准（法务/甲方验收需要）。

## 出具主体说明

报告以配置的公司名义出具（见 assets/config.json）。正式场景（应用商店上架、等保测评、项目验收）须由具备 CNAS/CMA 资质的第三方机构出具并盖章；自检报告仅作内部整改依据。此点须在「评估结论」中如实说明，模板已内置该段，不要删除。

## 生成流程（md → docx）

不手工建 Word。数据整理进 `assets/templates/结论报告.md` 的副本（占位符【】替换为实际值），再用包内 scripts/md2docx_convert.py 转换（--toc 生成目录域，见 SKILL.md），版式自动统一：GB/T 9704 字体字号、多级自动编号、三线/网格表样式、目录域。定稿前删除附录 D。
